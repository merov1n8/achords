# ADR-0021: Machine migration via encrypted export/import

Status: Accepted (2026-11-19; proposed earlier the same day)

- Context: The owner develops on a MacBook and runs production on a Mac Mini; customers will also move installs between machines. Rebuilding config, skills, memory and secrets by hand is error-prone.
- Decision: All state lives under a single `ACHORDS_HOME`. `achords export <file>` writes one archive: `ACHORDS-EXPORT-1` magic, a JSON header (KDF parameters, salt) and AES-256-GCM over the gzipped payload, with the key derived from a passphrase (scrypt N=2^17, r=8, p=1; 12+ characters) and the header as AAD. The payload holds every file under `ACHORDS_HOME` except `run/`, `logs/`, `vault.db` and `master.key`, a consistent `VACUUM INTO` snapshot of `core.db`, and the vault secrets. Secrets exist in plaintext only inside the encrypted payload and in memory; on import they are stored with the target machine's own master key. The gateway must be stopped for export; afterwards the source queue is paused. Import requires an empty data folder, validates every path before writing, rewrites the old data path in agent manifests, clears web sessions and pairing codes, migrates older schemas (refuses newer ones) and starts paused. Not exported: subscription CLI logins (ADR-0004), Tailscale identity, model weights. Standard library only.
- Consequences: Every new piece of state must live under `ACHORDS_HOME` (covered by the round-trip test). The archive is built in memory, which is fine for typical installs; very large workspaces may need streaming later. A lost passphrase means the export is unrecoverable.
