# ADR-0051: Agent runs with any website in an Apple container

Status: Accepted (2026-11-21), owner decision of the same day. Claude models only for now; first live agent run by the owner.

- Context: ADR-0011 planned containers for agents that read untrusted input; ADR-0038 chose isolation C (no containers) first. `network.allow: ["*"]` (ADR-0035) already means any website, but the run then works on the Mac with the owner's user: one injected instruction away from everything that user can read. Apple's `container` tool (lightweight Linux VMs, one per container, Homebrew `container` 1.7.1) now runs on the target machine.

- Decision:
  - **Manifest.** `container: true | false`, only next to `"*"` in `network.allow` (anywhere else it is a validation error). Absent = true with `"*"`, so every open-web agent runs in a container unless the owner opts out. The web agent form shows the checkbox "Run in an Apple container" only when `*` is listed, default on, with a red warning when switched off. Agent change proposals cannot change it; a change that drops the last `*` drops the key, and a switched container is listed in the owner's approval message. Without `*` nothing changes. `container: false` with `*` means unrestricted network on the host, within the agent's folder rules (as before).
  - **Wrapper, not a new provider.** The run request gets a container spec; `cli-claude` spawns `container run --rm -i --init --progress none --name <name> --cpus 4 --memory 4G --mount … -e NAME … -w <cwd> <image> claude …` with the claude arguments unchanged. The prompt goes on stdin as before.
  - **Mounts: only the run's folders, at their host paths** (and their real paths when a symlink is involved), so prompts, `--add-dir` and allow rules stay valid: the working folder and `fs.write` roots read-write, `fs.read` roots read-only, a per-run folder with the MCP config read-only (`container` shares folders, not files), and, when the run has MCP servers, the code they need read-only (`node_modules`, `packages`, `apps/gateway` of the checkout; not the rest of it). Nothing else of `$HOME`, not `~/.achords` (vault, databases), not the Keychain. Missing read roots are skipped; files cannot be shared and are refused.
  - **Secrets never on argv.** `-e NAME` copies the value from the `container run` client's environment, which is the run's own env (API key or token) plus the gateway's; only the run's own names are passed in.
  - **Claude login.** The Keychain is not reachable from Linux: subscription runs use a long-lived token from `claude setup-token`, stored write-only in the vault as `claude-oauth-token` (Settings → Model access → Claude → "Token for container runs") and given as `CLAUDE_CODE_OAUTH_TOKEN`. Without it the run fails with that instruction. API mode passes `ANTHROPIC_API_KEY` as today.
  - **OpenAI (codex) and Gemini: refused in a container for now**, with a plain message at run start (choose a Claude model or switch the container off). Their subscription logins are files in the home folder or the Keychain that we do not copy (ADR-0004); API mode would work in principle, but codex's permission profile is built from macOS host paths (its own packages, PATH folders under home) and its Linux sandbox inside a VM is unverified. Stage 2 after a live probe. Local models get no tools, so they run as before.
  - **Hub and integrations from the VM.** MCP servers in the config start with the image's `node` and reach the gateway at the host's address on the container network (`container network inspect default`, `192.168.64.1` by default). The gateway keeps listening on 127.0.0.1 and adds a second listener on exactly that address, never `0.0.0.0`: it accepts connections only from the network's subnet, serves only `/api/agent/*` (run tokens and one-time tickets, as on loopback), and its `host:port` joins the Host allow-list. The address exists only while a VM runs, so the listener binds on the first container run (retrying for up to 2 minutes while the run's VM starts) and stays; the launcher retries its ticket fetch for a few seconds while nothing answers. Builtin integration servers use the image's `node`; servers started with `npx`/`uvx` find them in the image. Local apps (Blender, Unity) are not reachable from the VM.
  - **Image.** `seed/container/Dockerfile`: `node:22.23.5-bookworm-slim`, git, python3, `uv`/`uvx` 0.13.9, `@anthropic-ai/claude-code` 2.1.328 (the version the adapter was verified with), no auto-update. Tag `achords-agent:<first 12 hex of sha256(Dockerfile)>`. Built with `container build` on first need (the task waits without losing an attempt, about a minute) or by `achords container build`; any change to the Dockerfile, arriving with an update, gives a new tag and a rebuild on the next container run; older `achords-agent` images are removed afterwards, and the builder VM is stopped if it was not running before. A failed build fails that task with the build's last output; the next run tries again.
  - **Stopping.** Signals to the `container run` client do not stop the VM. Container names are `achords-run-<hash of ACHORDS_HOME>-<uuid>`; timeout and cancel run `container kill <name>`, `achords kill` kills every running container of this install, and a starting gateway stops the ones a crashed predecessor left. Other installs (a dev checkout, tests) are never touched. `--rm` removes them after they stop.
  - The agent's system prompt says it runs in an isolated Linux container with only its own folders.

- Consequences: An agent with any website no longer sees the owner's files, keys or other projects; a prompt injection reaches only its own folders, the hub's agent API (run-token bound, as before) and the internet. The run costs a VM start (about a second) and up to 4 CPUs / 4 GB while it runs. The token from `claude setup-token` is a long-lived credential: revocable in the Claude account, never shown again by achords. Containers run Claude models only until codex and Gemini are probed in Linux. The `container` tool and its service are a new prerequisite only for agents that use it; without them those runs fail with how to install it.
